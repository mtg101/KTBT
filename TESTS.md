# KTBT: Testing

How we test KTBT: what's checked automatically, what still needs a human, and the conventions tests follow. Setting up the test framework is covered in [TOOLCHAIN.md](TOOLCHAIN.md#7-testing-gdunit4), and how the tests were first built is the Tests stage in [DEVLOG.md](DEVLOG.md).

## The approach

KTBT's core rule is **the game owns the facts; the AI owns the flavour**. The game decides the time, menu, prices, bills, titles and who knows whom, and it checks everything the AI produces before using it. Those rules are what keep a game full of AI-generated characters coherent, so they're what the tests protect.

- **Automated tests** check the game's rules and flow. They use a **fake AI** with canned replies, so they're fast, run without a GPU or Ollama, and give the same result every time.
- **Playtesting** checks the parts tests can't judge: whether characters feel right, whether dialogue reads well, whether it's fun to watch. For an AI-driven game, a human reading the output is still the main quality check.
- **AI quality runs** sit in between: batches of real AI generations, counted rather than pass/fail.

**Framework:** [GdUnit4](https://github.com/godot-gdunit-labs/gdUnit4) (v6.2.0 from the Godot Asset Store; version notes in [TOOLCHAIN.md](TOOLCHAIN.md#pick-the-right-version)). Chosen over GUT for its click-through scene testing, built-in mocks, and VS Code and GitHub integration.

## Test layers

- **Rule tests (unit):** pure functions with no AI and no scene. Examples: `Menu.resolve("Gyeran-mari")` gives `gyeran_mari`; `format_won(12000)` gives `₩12,000`; the bill adds up; an 18-year-old customer is rejected; an order with pizza is rejected; an Ajusshi described as an ajumma is rejected; a line saying "soju" when beer was ordered is rejected; "Name:" prefixes are stripped from dialogue. *From the Tests stage.*
- **Click-through tests (functional and UI):** load a real scene with the fake AI plugged in, click buttons the way a player would (so a disabled or covered button makes the test fail), wait for signals, then check the result. Example: a customer turns up, and the test checks the order line and conversation reach the transcript, the takings rise by exactly the bill, the customer leaves and the counter clears. Also covers failures: the AI keeps giving bad replies (the soju fallback), or Ollama isn't running. *From the Tests stage.*
- **Save/load tests:** save a bar, load it back, and check nothing was lost or changed. *Done (`test_save_store.gd`, `test_bars.gd`); saves made mid-conversation will need tests when resuming mid-visit is built.*
- **Visual tests:** screenshot a scene and compare it with an approved image, to catch broken layouts and clipped text. These need a real display rather than headless mode. *From the Real art, sound and polish stage, once the art settles.*
- **AI quality runs (not pass/fail):** generate a batch of real customers or visits with the actual model and count problems: rejection and retry rates, backwards names, wrong titles, mismatched orders. Useful for tuning prompts and for comparing models (Llama, Gemma, Qwen). *Whenever we tune prompts or try a new model.*

## How the click-through tests work

- **Real scene, real clicks:** each test loads a real scene (`scenes/visit.tscn` or `scenes/title.tscn`) with GdUnit4's scene runner, and `_click` sends the mouse moving over a button, pressing and letting go straight into the game's viewport. The viewport picks what's under the mouse just as it does for a real click, so a disabled or covered button fails the test. (Not gdUnit's `simulate_mouse_*`: they move the real mouse pointer while tests run, and in headless runs on Windows the clicks never arrive.)
- **Offline AI:** tests set `AiSettings.override = {"backend": "canned"}`, so no Ollama is needed. `CannedAi.scripted` queues exact replies (including bad ones) that are used before the normal canned ones.
- **Test hooks:** every switch the tests use is in `scripts/test_hooks.gd` (customers invented ahead are off in tests, `prepare_customers`, since they'd use up scripted AI replies early) (the game reads them as `Hooks.<name>` and never sets them): time scaled right down (`pause_scale_override`), a fixed `random_seed`, the clock held (`run_clock`), fixed stays, moods for company, chat chances and genders, the cat held still, no strollers, every look offered, no founding regulars, a fixed roll for becoming a regular, and each extra AI call (memories, reactions, diaries, recaps) off unless a test turns it on; bubbles off, captions on but unpaced; and where saves, night logs and transcripts go. `Hooks.for_tests()` sets them all (and the hooks in other scripts: `SaveStore.folder`, `NightStats.folder`, `AiSettings.override`, `CannedAi.scripted`, `Ai.simulate_unreachable`, `Ai.canned_think_seconds`, `Ambience.make_sound`, `Ambience.settings_path`) before each test; `Hooks.restore()` puts them back after.
- **A shared base for scene tests:** `tests/support/bar_test.gd`, which the visit, night and bars tests extend, does the before and after for every test, gives each suite its own folders (its `TEST_SAVES`, `TEST_STATS` and `TEST_TRANSCRIPTS`), and has the shared helpers (`_wait_until`, `_click`, `_transcript`). A suite adds its own setup in `_setup()` (its seed, whether the clock runs).
- **Warnings are errors:** unused variables and parameters, shadowing and confusable declarations stop a script loading, in the game and the tests, so they're fixed when they appear.
- **Headless from the command line:** gdUnit's runner, `addons/gdUnit4/runtest.cmd --godot_binary <your Godot> -a res://tests -c --headless --ignoreHeadlessMode`, runs every test with no window, so nothing takes the mouse or the focus (a VS Code task can run it). The editor's GdUnit panel still works, but brings the game window forward for each scene. Where each test night's transcript and stats went isn't printed during tests (`Hooks.print_paths`).
- **On every push:** `.github/workflows/tests.yml` runs all the tests headless on GitHub (offline mode, so no GPU or Ollama); the result shows on each commit, with the report kept with the run.
- **Customers arrive through `_arrive()`:** there's no Next customer button any more, so tests call the scene's `_arrive()`, the same method the game uses when someone turns up (several at once for a crowd, as if they turned up together), so arrivals are counted exactly as in play.
- **Separate stats and transcript folders:** like saves, tests point `NightStats.folder` and `Visit.transcript_folder` at their own folders, so test nights don't fill the real stats logs or the project's `logs/`.
- **Results on disk:** every run writes a report to `reports/report_N/` in the project (the editor reuses `report_1`; the command line numbers a new one each run) (`results.xml` and `index.html`, kept out of git), so failures can be read from there instead of copied from the GdUnit panel.
- **Waiting:** tests wait a frame at a time until the scene isn't busy, with a time limit, rather than sleeping for fixed times.
- **Let layouts settle before clicking:** containers (like the title screen's) position their children over the first frames after a scene loads, so the click helper waits a few frames before aiming. A button also fires on mouse *release*, so after clicking, tests wait for the effect rather than checking straight away.
- **No real scene changes:** switching scenes would replace GdUnit's own test runner, so tests set `Game.change_scenes = false` and check `Game.requested_scene` instead.
- **Separate save folders:** tests point `SaveStore.folder` at their own `user://test_saves…/` folder and empty it before and after each test, so real bars are never touched.

## Conventions

- **Location:** tests live in `tests/`, mirroring `scripts/` (e.g. `tests/test_menu.gd` tests `scripts/menu.gd`).
- **Naming:** test files start with `test_`; test functions describe the behaviour, e.g. `test_order_mentioning_unordered_item_is_rejected()`.
- **Rules live in `scripts/rules/`:** game rules and validators stay out of scene scripts, one file per area (see ARCHITECTURE.md), so tests can call them without loading a scene.
- **Fake AI:** scenes take the AI through one object (`ai.gd`), and tests swap in a fake that returns scripted replies, including deliberately bad ones. `ai.gd`'s own checking and retrying is tested against a fake Ollama (`tests/support/fake_ollama.gd`), which answers with scripted replies and keeps every conversation it was sent. The game's **canned AI** (offline mode, for machines without a suitable GPU) is built on the same fake, so tests and offline play share one implementation.
- **Fixed randomness:** tests set a fixed random seed, so the moment, entry side and visit length are the same every run and failures can be reproduced. But a new dice roll anywhere in the game shifts every roll after it, so a test that needs something particular (a customer's mood for company, the cat staying put, the rain gear) sets it with a hook rather than relying on what the seed happens to give: two visit tests broke on GitHub that way when the specials and cravings added rolls. Scenery that comes and goes by itself (the neon, steam, the cat prowling) has its own dice, so it never shifts the game's.
- **No waiting around:** tests set pauses to near zero, so a whole visit runs in a second or two. The night's clock is scaled the same way, so a whole night (6pm to 3am) runs in a few seconds.
- **Named nodes:** UI nodes that tests interact with have fixed names (`Transcript`, `TakingsLabel`, `TryAgainButton`, `SoundToggle`, `SoundVolume`, `MusicVolume`, `Tarp`, `Loading`, `Customer0`…), so tests don't break when the layout changes.
- **No real AI in the test suite:** the suite must pass with Ollama switched off. Real-model checks belong in AI quality runs.

## Bugs become tests

When we fix a problem, we add a test that would have caught it, so it can't creep back. These tests have `regression` in their name and point to the matching entry in [LLM-TUNING.md](LLM-TUNING.md). Fixed issues covered so far:

- **Owner titles:** the owner prompt no longer asks the AI for a title, and an archetype using a term for the other gender is rejected (whole words only). `test_rules.gd`, `test_prompts.gd`.
- **Double opening and mismatched orders:** a visit's customer prompt has no opening line, and an order line mentioning a drink or main that wasn't ordered is rejected (except soju and beer with somaek), a side it asks for is added, and a somaek order has to ask for somaek. `test_rules.gd`, `test_prompts.gd`.
- **Strangers acting like regulars:** order and conversation prompts include the first-visit note. `test_prompts.gd`.
- **Not listening to each other (partly fixed):** serving appears in the transcript as a stage direction, and the "what just happened" recap comes after the conversation in every dialogue prompt. `test_prompts.gd`.
- **Talking about food that isn't on the table:** the style guide names no menu items, and a conversation line mentioning food that isn't on the table is rejected. `test_rules.gd`, `test_prompts.gd`.
- **Unrealistic orders:** orders need a drink and a food; two mains or two drinks are rejected unless the customer is hungry or having a rough night; the prompt asks for one drink. `test_rules.gd`, `test_prompts.gd`, `test_menu.gd`.
- **Everyone orders exactly once / later orders too early / sounding like a first order:** later-order limits, fried rice only after a main, the "more" wording check, the odds, and the turn spacing (never the first reply or last line, two later orders spaced apart). `test_rules.gd`, `test_prompts.gd`.
- **The cat as it really is:** stroking it, or talk of it on a lap, is rejected unless it's on the lap of someone in the conversation. `test_rules.gd`, `test_prompts.gd`, `test_visit.gd`.
- **Same names, slow arrivals:** a customer's name and gender come first, in their own quick step; a name that's at the counter (or the owner's) is rejected; the prompt lists names to avoid. `test_rules.gd`, `test_prompts.gd`, `test_canned_ai.gd`, `test_visit.gd`.
- **Copied appearances, names nobody said, regulars in chats, rice cakes:** a customer prompt with a game-decided look lists no earlier appearances; strangers are described as they look; chat prompts say everyone's seated and new here; "spicy rice cakes" is tteokbokki. `test_prompts.gd`, `test_rules.gd`, `test_visit.gd`.
- **Later orders that ask for more than they get:** "another tteokbokki" without tteokbokki in the order is rejected, "this/the tteokbokki" is fine, rice asked for by an alias is added to the order (if there's room), "fried rice" isn't also read as "rice", and conversation can still mention rice. `test_rules.gd`.
- **Wrong pronouns in the diary and recap:** the night's facts carry everyone's pronoun, beside each name and in a closing line; older facts without them still read. `test_rules.gd`.
- **"One more soju" served as somaek:** a somaek order must ask for somaek (or soju and beer together, or "the usual"). `test_rules.gd`.
- **Hover hints shown as raw BBCode:** an apostrophe in a hint ("ma'am") broke the tag; hints are made safe, and checked through a real RichTextLabel. `test_rules.gd`.
- **The street:** a test of umbrellas that rolled the dice would have failed about one run in 14 (someone running for it), so street tests fix the gear and the group size. `test_visit.gd`.

## Test plan: Regulars and relationships

Most of the risk in this stage is in rules the game owns, so most of it can be tested without the AI. Tests are written with each step.

- **Rule tests:** the regulars model as functions that take their dice rolls (becoming a regular from each verdict, pull rising, falling and fading, dropping off below the threshold, favourite nights and usual hours); **who calls whom** as a full grid (speaker and listener gender × older, same or younger × stranger or close × owner or customer), with must-never checks (no oppa/hyung/eonni/nuna to someone younger or before they're close, no "ajumma" to a young woman, no imo/samchon from someone older than the owner), and the line checker for each term and its common spellings; who knows whom (names only once said, "the usual" only once real, "9 nights ago"); memories and verdicts (verdicts from the game's options, things that stick backed by the transcript).
- **Prompt tests:** first-timer, regular and founding regular prompts carry exactly what the game knows; every conversation has each pair's address line; the "can I call you eonni?" direction only when set up, and only once.
- **Offline mode and saves:** canned replies for every new ask pass the game's checks; regulars round-trip (look, Hangul, pull, memories); an older bar gets its two founding regulars once.
- **Click-through tests:** a new bar's two founding regulars; a forced regular arriving isn't reinvented (a log of AI asks by purpose shows no name or details ask), shows ★★ and their saved look; a scripted "loved it" with a fixed roll makes a regular, "didn't enjoy it" doesn't; a real usual is ordered and served; the "eonni" moment happens once, and the term is allowed only after it.
- **Simulated months (the runaway guard):** the regulars model run over 100 nights, many seeds, no scene or AI, checking the number of regulars stays in a sensible band, their share of arrivals stays believable, people who stop coming fade out, founding regulars usually last, and nobody monopolises the bar. Rerun whenever the numbers are tuned.
- **Whole-night checks:** after every click-through test, the transcript is checked for names used before they were said, address-rule breaks, "the usual" from first-timers, and regulars' looks changing.
- **For playtests with the real AI:** regulars in the stats panel and night log (new versus returning, who became a regular or faded, the verdicts), and new rejected-reply kinds (address rules, names not yet known, "the usual").
- **New test hooks:** a fixed "comes back" roll, forcing a particular regular to arrive, letting nights pass without playing them, and the log of AI asks by purpose.
